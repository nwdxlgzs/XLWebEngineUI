# XLWebEngineUI 库体积调查报告

调查日期：2026-11-03（Asia/Shanghai）。单位统一为 MiB（1 MiB = 1,048,576 字节）。本轮只取证和分析，未修改引擎、依赖配方或 SDK 打包行为。

## 结论

当前七百多 MiB 的静态库主要由 **Debug 对象及其调试/链接元数据、完整第三方静态归档合并、Skia 闭包中重复收录的对象**构成。完整 SDK 同时携带静态库、动态库和 WebTest，静态库占 SDK 解包大小的约 94%–95%。DLL/so 的实际部署大小远低于静态归档大小。

已确认的可改进问题有两个：**静态库的调试信息没有随独立 Symbols 包分离；Skia 已内含的辅助对象又被独立归档重复合并。** ICU 数据已经裁剪为压缩后 4.16 MiB，继续只盯 ICU 不能解决静态库体积的主要问题。

本报告量化调查开始时最后完成的 ICU 裁剪阶段包，源指纹 `96c921031d2f26af7596a00d6fb086abc5d30be9494b995af6e0aec8af62c0f0`。调查时另有 outline 开发构建在运行，工作目录产物会变化，不与固定包混合统计。

## 1. 实际有多大

| 固定样本 | SDK 压缩包 | SDK 解包普通文件合计 | 静态库 | 动态库 | WebTest 程序 |
|---|---:|---:|---:|---:|---:|
| Windows x64 Debug 阶段包 | 184.62 | 739.74 | **701.78** | **35.05** | 2.55 |
| Linux x64 musl Debug 阶段包 | 166.60 | 773.83 | **728.05** | **42.52** | 1.98 |

- Windows 静态库精确为 **735,867,304 字节**，占解包 SDK 的 **94.87%**。在 ZIP 中它单独占用 178,755,975 字节，即整个压缩包的约 **92.34%**。
- musl 静态库精确为 **763,415,200 字节**，占解包 SDK 的 **94.08%**。TAR.GZ 为整流压缩，不把压缩后字节伪分配给单个成员。
- 独立符号包另计：Windows 26.39 MiB，musl 34.54 MiB。上表不包含它们；Linux 的 so 符号链接不按目标大小重复累计。

因此，下载完整开发 SDK、查看静态归档、部署动态库是三个不同口径。动态库消费者通常只需部署所用动态库、程序及必要运行文件；静态归档的全部字节不会原样成为最终程序。

## 2. 最大原因：调试信息仍留在静态库

逐对象解析 COFF/ELF，按实际文件节大小统计；只在解包临时副本上执行 `llvm-objcopy --strip-debug`，保留并还原 Windows 原始 `.res` 成员：

| 项目 | Windows Debug 静态库 | musl Debug 静态库 |
|---|---:|---:|
| 原始归档 | 701.78 | 728.05 |
| 其中直接调试节 | **363.77** | **312.94** |
| 对象代码节 | 52.25 | 40.56 |
| 数据和其他文件节 | 22.54 | 26.36 |
| 对象符号/字符串表 | 113.09 | 74.39 |
| 对象重定位记录 | 64.22 | 195.58 |
| 对象头和未单列结构 | 50.25 | 50.19 |
| 归档索引、成员头、名称及对齐 | 35.65 | 28.03 |
| **副本去除调试信息后的实测大小** | **277.07** | **249.86** |
| **实测减少** | **424.70（60.52%）** | **478.19（65.68%）** |

`--strip-debug` 还会删除指向调试节的重定位及相关符号/结构，故减少量大于调试节本身；不能把这两项相加。上表也说明静态归档除了机器码，还有大量供链接器使用的元数据。

根因在构建和安装策略：

1. [CMakeLists.txt:28](../CMakeLists.txt#L28) 将 Windows `/Zi` 替换成 `/Z7`，注释明确要求把静态库调试信息放进每个对象。这使 SDK 不依赖构建机的编译器 PDB，但同时显著增大 `.lib`。
2. [CMakeLists.txt:125](../CMakeLists.txt#L125) 在 Windows Release 也追加 `/Z7`；Linux 两配置引擎对象均加 `-g`。[tools/deps.py:359](../tools/deps.py#L359) 对 Windows Skia 两配置都加 `/Z7`。
3. Symbols 包收集的是 DLL/WebTest 的 PDB 或 `.debug`。Linux [StripInstalledSymbols.cmake.in](../cmake/StripInstalledSymbols.cmake.in#L1) 只处理安装后的 so 和 WebTest，**没有处理静态 `.a`**；Windows 也没有移除静态 `.lib` 内的 CodeView。

所以“PDB 已单独打包”不等于“静态库已分离调试信息”。当前结果是实际构建策略造成的，而非 ZIP 中误放了 PDB。副本实验只证明可移除的字节规模；本轮没有对裁剪后的库进行链接消费或功能验收。

## 3. 完整第三方归档合并，Skia 是第一大来源

当前静态 SDK 将全部选中私有归档经 `ADDLIB` 合并并统一隔离符号，见 [CMakeLists.txt:106](../CMakeLists.txt#L106) 和 [merge_archive.py:60](../tools/merge_archive.py#L60)。它是可独立交付的依赖闭包，合并时没有按当前调用路径做链接器式裁剪。

下表为输入归档的原始文件大小，合并前测量；包含归档自身索引和调试信息，**不能与上节的分项相加**：

| 输入依赖族 | Windows Debug | musl Debug |
|---|---:|---:|
| **Skia 及其辅助归档** | **467.78** | **454.65** |
| HarfBuzz 主库 | 75.28 | 87.60 |
| ICU common + i18n 代码库 | 60.56 | 54.69 |
| SDL3 | 24.93 | 15.55 |
| Lexbor | 11.92 | 10.34 |
| QuickJS-NG | 3.96 | 2.71 |
| 私有 X11 平台栈 | — | 29.65 |

其余为 FreeType、图片解码、压缩库等。引擎自身的合并对象有效载荷约为 Windows 35.60 MiB、musl 35.70 MiB，含引擎对象调试信息和内嵌 ICU 资源，不能全部当成引擎机器码。

Skia 构建保留 Ganesh/OpenGL、SkSL、文字整形和段落等能力，Debug 还引入 SPIR-V 验证路径，见 [deps.py:342](../tools/deps.py#L342)。这些会放大完整静态归档。当前运行时主要走 Raster；但**已编进归档不代表全部被链接进 DLL**，也不应为减小数字删除仍在总目标内的 GPU 能力。PDF/SVG/XPS 当前构建已关闭，不能把它们列为这批包的体积来源。

## 4. 已证实的重复合并

对合并后每个成员有效载荷做 SHA-256，发现两平台 Debug 都有 **85 个多余的完全相同成员**：

| 已包含在 Skia 主归档、同时又单独合入的对象 | 多余成员数 | Windows 多余有效载荷 | musl 多余有效载荷 |
|---|---:|---:|---:|
| SPIR-V Tools validator | 53 | 59.60 | 52.84 |
| SPIR-V Tools core | 27 | 14.35 | 10.99 |
| Expat | 3 | 0.81 | 1.16 |
| skcms | 2 | 1.01 | 0.84 |
| **合计** | **85** | **75.78** | **65.83** |

原因是 Skia 主归档已带这些成员，而 [sdk_inputs.py:71](../tools/sdk_inputs.py#L71) 仍收集同目录辅助归档；`merge_archive.py` 对所有输入执行 `ADDLIB`，未检查内容重复。现有过滤处理了 Brotli 编码器、HarfBuzz 辅助库、WebP decoder 别名等，却没有识别这一层成员重叠。

这是真实冗余，不是“函数名相似”的猜测。75.78/65.83 MiB 是多余对象有效载荷，未算可随去重缩小的索引；也包含调试信息，**不能再与去调试信息的收益直接相加**。DLL 通过链接器抽取归档成员，不能据此推导 DLL 也多出相同大小。旧 Release 两端也各有 2 个重复 skcms 成员，分别约 0.44/0.18 MiB。

## 5. 动态库的体积来自哪里

Windows 阶段 DLL 为 35.05 MiB，其中 `.text` 文件节约 24.69 MiB，`.rdata` 约 8.93 MiB；DLL 本身没有静态归档中数百 MiB 的对象调试节。

对与该 DLL 配套的 Symbols ZIP 校验哈希并解析 PDB，获得已链接 `.text` 的来源。下表覆盖 24.28 MiB 可归属代码贡献，未计各函数间对齐间隙；**只衡量代码，不等于各依赖占 DLL 全文件的比例**：

| 来源 | 代码贡献 MiB | 占可归属代码 |
|---|---:|---:|
| Skia | **9.25** | **38.09%** |
| SDL3 | 3.29 | 13.57% |
| HarfBuzz | 2.80 | 11.54% |
| CRT、系统及其他对象 | 1.58 | 6.52% |
| 引擎自身 | **1.46** | **6.00%** |
| ICU | 1.28 | 5.25% |
| QuickJS-NG | 1.21 | 4.99% |
| 其余文字、图片、压缩与 DOM 依赖 | 3.41 | 14.03% |

Skia 中可明确归入 Ganesh 的代码贡献约 0.053 MiB，SkSL 约 1.09 MiB；本样本没有 SPIR-V Tools 的 `.text` 贡献。因此不能把静态库中整个 Ganesh/SPIR-V 闭包的体积算成动态库可直接削掉的空间，SkSL 也可能被软件运行时着色路径使用。

musl 安装后的 so 已去除 DWARF，但仍保留普通本地符号和字符串表。在副本上执行 `--strip-unneeded`，从 **42.52 降到 31.41 MiB**，再减少约 11.11 MiB；WebTest 从 1.98 降到 1.51 MiB。这是进一步分离非运行时元数据的实测空间，本轮尚未验收处理后文件的动态加载与实际运行。

## 6. ICU 不是当前主要问题

两平台包内资源清单均显示：原始 ICU 数据 **10,470,976 字节**，Zstd 压缩后 **4,362,007 字节（4.16 MiB）**。这部分已从早期完整数据的 10,504,647 压缩字节降低约 58.5%。首次使用才解压的内存策略不会减少压缩数据在库文件中的占用，也不能用库文件大小推算运行时内存峰值。

4.16 MiB 约为当前 Windows DLL 的 11.87%，静态库的 0.59%。即便假设完全删除这份数据，也无法解决七百 MiB 静态库的问题，而且会损害文字能力。

需要区分 **ICU 数据裁剪**与 **ICU 代码裁剪**：[ICU 配方](../third_party/recipes/icu/CMakeLists.txt#L15) 仍收集全部 common/i18n 源码，主要关闭文件 IO 和动态加载；Chromium 数据 filter 不会自动减少这些代码对象。后续若做代码裁剪，须先证明文字、分段、规范化和未来标准能力的实际依赖，不能直接照搬一组宏或删除整个 i18n。

## 7. Release 是否就会很小

读取已保留的历史 Release 包作为参照，源指纹 `f355a0e85d57b2768bde2c2ad6c6773dd70bf0de6bba295c4a7d727a601cf17e`：

| 历史 Release 样本 | 压缩 SDK | 静态库 | 副本去调试后的静态库 | 动态库 |
|---|---:|---:|---:|---:|
| Windows | 76.36 | 206.00 | **80.54** | 25.18 |
| musl | 53.88 | 101.90 | **66.43** | 27.22 |

这些包是较早功能阶段，**没有当前 WebTest，ICU 仍为旧的完整压缩数据 10.02 MiB**，也未包含当前全部布局/编辑功能。不能把上述大小写成当前版本切换 Release 后的验收结果。

它们仍能证明“Release = 没有调试信息”不成立：Windows Release 静态归档中直接调试节达 113.87 MiB，主要是强制 `/Z7` 的 Skia；musl Release 仍有 23.82 MiB 调试节，其中私有 X11 输入归档贡献约 17.45 MiB。[platform_deps.py:111](../tools/platform_deps.py#L111) 明确使用 Release `-O2 -g -fPIC`。

当前 Debug 的未优化代码、断言、模板实例以及调试版第三方闭包，进一步放大了体积。只在最终 SDK 外层改用更强压缩，不能消除这些结构原因。

## 8. 建议顺序与验收要求

| 优先级 | 建议 | 已有量化依据 | 实施后应验证 |
|---|---|---|---|
| 1 | 合并时按内容识别并消除重复对象，保留完整逻辑依赖及许可 | Debug 多余有效载荷 75.78/65.83 MiB | 实际静态消费者、宿主同名依赖冲突、私有符号/资源成员及增量重合并 |
| 1 | 设计静态库的发布与调试交付策略，保留可调试开发版本，同时提供优化、去调试的发布静态库 | Debug 副本 701.78→277.07、728.05→249.86 MiB；历史 Release 也有明显空间 | 静态消费、最终宿主调试/符号化、C/C++ ABI、资源和真实绘制；DLL 的 PDB 不能替代静态宿主调试信息 |
| 2 | 在正式发布阶段测量同一源码的 Release/尺寸优化和按节裁剪效果，评估 LTO/ICF | 当前阶段默认打 Debug；历史 Release 说明方向，但不是同版本收益 | 定向功能及 ABI 回归、运行性能、链接兼容性；最终发布仍走完整 CI |
| 2 | musl 发布安装副本进一步处理非必需本地符号，构建树和独立符号仍保留 | Debug so 副本 42.52→31.41 MiB | 包内 WebTest、dlopen/dlsym、关闭/重建和静态/动态边界 |
| 3 | 完整 SDK 继续包含双库；如需降低试用下载量，额外提供 Runtime/WebTest 试用包 | Windows SDK 压缩空间约 92.34% 来自静态库 | 新包内容、许可、哈希及解包后的实际运行；不能用试用包替代完整 SDK |
| 4 | 评估 ICU 代码和 Skia 依赖收集粒度，保持完整引擎总目标 | 静态合并保留当前未抽取的对象；数据裁剪不等于代码裁剪 | 先建立真实调用/资源依赖证据，再决定技术拆分；不删除 GPU、媒体等总目标 |

最先值得处理的是重复归档和静态调试交付，收益证据最清楚。更换排版/绘图库、移除 Unicode、删掉尚待实现的能力，都不是本轮证据支持的第一步。

当前 `RESOURCE-BUILD-INFO.json` 的实际私有归档清单没有 libvpx、Opus、Vorbis、libogg 或 HTTP/TLS 库；不能把尚未进入最终 SDK 的媒体库，或不存在的网络栈，算作本批包的原因。下载源码/构建缓存的磁盘占用也属于另一个口径。

## 9. 取证范围与复现

机器可读结果：[report.json](../build/reports/library-size/20261103T140059Z-9fe06225/report.json)。持久化分析入口：[tools/analyze_library_size.py](../tools/analyze_library_size.py#L1)。它读取普通归档成员、COFF/ELF 文件节、SHA-256 重复组及 Windows PDB 代码贡献；原始库和归档保持只读，剥离实验全部在 `build/` 临时副本执行。

四个 SDK 的哈希均与原报告匹配；全部私有输入归档均存在并逐个校验哈希；Windows 配套符号包也校验哈希。COFF/ELF 调试节解析已分别抽样与 `llvm-size -A` 对照一致，四份去调试副本的代码/数据节字节数均保持。Python 3.8 语法、报告链接、分项对账和管理文档检查通过。按普通文件物理字节统计，不把 `.bss`、地址空间、符号链接目标重复计入大小。

本轮没有重编引擎、执行完整 CI、生成新 SDK 或验收瘦身产物，也没有测量运行内存、速度或当前完整功能状态。分析副本已由临时目录机制清理；Windows→WSL GC 均已退出，未发现剩余候删或验证暂存；机器报告按类别保留最近三份。全部优化项仍为后续实施建议，不能将本报告当成瘦身已经完成。
