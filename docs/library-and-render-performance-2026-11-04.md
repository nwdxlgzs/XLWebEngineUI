# 当前库组成与网页首帧、滚动性能调查

日期：2026-11-04（Asia/Shanghai）。调查覆盖用户指定的 `tests/user-dev-tests` 三个原始网页。本文给出实际测量与源码对应关系，没有实施运行时优化，也没有修改原始网页或 RAW。

**结论：当前 Windows 静态库最大的组成是 DXC，其次是 Skia、SwiftShader、ANGLE；完全重复对象已为零。网页卡顿的主要原因是纯滚动仍重新构建整个文档的布局，连带反复计算盒样式、文字布局及 AX 树。切换 GPU 后端不能绕过这些 CPU 工作。**

全部机器证据及校验值见 [汇总报告](../build/reports/library-and-rendering/20261104T014346Z-7e573211/report.json)。体积和耗时是两组独立测量，不能从库文件大小直接推算运行速度。

## 1. 样本与方法

- Windows 11，Intel Core i7-11800H（8 核/16 线程），NVIDIA GeForce RTX 3060 Laptop GPU。仅本机开发环境，没有 Win7、Release 或其他硬件性能验收。
- Windows 采用调查开始时已完成的 CSS 嵌套阶段包 `20261104T011958Z-aa141ba6`，源指纹 `6b95305861f6c34072dbdce08de7b5cc5dd3855e97d1ab845f4378b123f67b0e`；DLL SHA256 `8b09bba5f9174008f028ef237fab66c42364fdc84e5ed49cae9273e52b747028`。
- Linux 体积采用当时已通过验收的圆角阶段包 `20261104T002133Z-ebdfd836`，源指纹 `ddbc3701359e353a158a07c1da23eec8d3b5b35ba972512ec08984a45491112f`。没有用当时报告为 failed 的 Linux 嵌套包冒充成功交付。两个平台不是同一功能阶段，不能据此计算平台实现优劣。
- 包和对应私有输入归档均核 SHA256；静态库逐对象读取 COFF/ELF，Windows DLL 通过配套 PDB 解析已链接代码贡献。MiB=1,048,576 字节。
- 性能使用固定的 Windows DLL，每个页面/后端在新进程运行，960×640。比较 Raster、AUTO（实际 D3D12）、ANGLE OpenGL（实际 active=5）；不是只看请求的后端名称。
- 第一组不执行脚本，以隔离纯 HTML/CSS 滚动；第二组启用原始内联脚本、Windows 隐藏原生窗口和 UIA，包含像素读回、SDL 提交。使用六次连续 24px 程序滚动，另向 HWND 投递 `WM_MOUSEWHEEL`，确认 Windows→SDL→引擎链路；这不是物理鼠标或屏幕端到端延迟测量。
- 为拆分阶段，只在 `build/` 的源码副本加入 RAII 计时器，使用原 Debug 编译选项和既有依赖链接独立诊断 DLL。原产品源码/库没有加入计时分支。九个“页面×后端”组合的诊断 DLL 与原 DLL 最终 RGBA SHA256 全部一致；耗时结论也由未插桩的原 DLL 复验。
- 所有依赖和引擎均为当前 Debug 路线，Windows 有 `/Od /Ob0 /RTC1`。下文是当前实际包的性能，不外推成 Release 的最终表现。新进程不等于清空 OS 文件缓存或显卡驱动缓存，首帧是实测新进程首调，而非宣称绝对冷机数据。

## 4. 滚动为什么卡：主要根因有实际计时支撑

### 4.1 纯滚动触发完整文档布局，约占示例2帧耗时的 98%

[scroll_offset](../src/runtime/view_api.cpp#L192) 改偏移后设 `scroll_dirty=true`；[sync_document](../src/runtime/view_api.cpp#L614) 遇到这个标志就再次调用 `Document::layout`。该方法继续执行完整块/Flex/Grid/行内布局，再调用 [build_accessibility](../src/document/document.cpp#L442)。

原 DLL 的六次纯滚动：**每页均增加 6 次 layout_frames，而 document revision 不变**。它本应是视图坐标变化，却重新执行大量与偏移无关的工作。

诊断 DLL 的示例2 Raster 六帧平均：

| 阶段 | 每帧耗时 | 关系 |
|---|---:|---|
| `xl_view_render` 总计 | **1648.1ms** | 整帧 |
| `Document::layout` | **1622.4ms（98.44%）** | 含下面的布局与 AX |
| 块/Flex/Grid/行内布局 | 1433.4ms | 包含样式计算与文字入口 |
| `TextEngine::shape` 入口累计 | **937.6ms** | 包含缓存查找及真正文字布局；嵌在块布局中 |
| `box_style` 计算 | **287.6ms** | 不是每次重新解析 CSS 选择器，而是反复求盒子的计算值 |
| AX 树构建 | **189.0ms** | 属于 `Document::layout`，不应与其重复相加 |
| 真正绘制 | 20.0ms | 占比很小 |

这里的计时器有包含关系，不是互斥相加表。纯滚动时 `refresh_styles` 通常直接命中版本返回，选择器层叠不是本样本的主要开销；昂贵的是后续整个布局流程仍重新执行。

### 4.2 文字缓存容量和生命周期不足以避免重复工作

[TextEngine 缓存](../src/text/paragraph.cpp#L307) 用线性队列扫描，对每次 shape 先清失效 weak_ptr，再依次比较 runs/boxes/width 等键。它最多 **128 项／1MiB**，且只持弱引用；内在尺寸探测的临时段落也可能随探测结束失效。容量边界见 [paragraph.cpp](../src/text/paragraph.cpp#L880)。

在内容不变的每一帧：

| 页面 | `shape` 调用 | 命中 | 未命中 |
|---|---:|---:|---:|
| 示例1 | 195 | 115 | 80 |
| 示例2 | **2312** | **726** | **1586** |
| 差异观察页（无脚本） | 378 | 238 | 140 |

示例2每次滚动都重复相同规模的 1586 次 miss。大量入口来自 min/max 内在测量、实际布局以及嵌套布局，并不是用户正在输入或内容不断变化。整个页面每次重排都会重新创建本次布局的内在尺寸缓存，旧帧结果没有成为纯滚动可复用的布局结果。

这支持“保留布局、稳定缓存键、复用内在测量”作为优先方向，但**不能仅凭加大 128 这个数字就承诺性能**。本轮曾尝试扩大缓存的隔离对照；并行颜色开发更新了普通工作目录对象，两个尝试因链接输入代次不一致失败，未取得有效变体。失败日志已保留，本文不报告不存在的优化收益。

### 4.3 AX 每次重建，原生订阅另有额外成本

纯滚动也重建全树的角色、名称、状态和几何，而不仅更新可见矩形；示例2约 **189ms/帧**。这项即使未启用原生 UIA 也存在，因为公开 AX 查询共享该快照。

启用与 WebTest 相同的原生 UIA 后，示例2还额外花约 **38–43ms/帧**发布和比较语义更新。不能用关闭无障碍来替代优化；应保留语义与身份，只更新几何/可见性以及必要事件，并复用未变子树。

### 4.4 滚动几乎整帧重绘，尚无独立滚动合成

三个页面六次纯滚动的 `rasterized_pixels` 都为 **6×960×640**，每一步相当于全视口重绘。位置变化使现有 box/text 比较形成大范围损伤，没有保留滚动层并平移、只补新露出的条带。此项虽然目前被布局秒级耗时掩盖，布局优化后会变成需要处理的下一层瓶颈。

## 5. 首次打开慢的组成

HTML 文件只有约 14.4KiB、72.3KiB、94.2KiB。实际 HTML 加载调用多在 **2–4ms**；DLL 映射在初次探测为几十毫秒、后续缓存下可更低，均不能解释示例2的数秒首帧。

原生 D3D12 示例2的一次新进程实测：

- 后端初始化约 **273ms**，发生在首次 render 之前。
- 首次 render 约 **2941ms**，其中样式准备约 **232ms**、完整布局含 AX 约 **1906ms**、绘制含同步提交约 **447ms**、初次像素读回约 **299ms**。
- GPU 绘制内部 `flushAndSubmit(GrSyncCpu::kYes)` 约 **426ms**。第一次提交需处理此前积累的工作，包含着色器/管线等冷启动成本；本轮没有把它全部归为 GPU 执行时间或全部归为 DXC 编译。

示例1首帧 GPU finish 约 **762ms**，而后续只有约 **2ms**；读回也从第一次约 **252ms**降到后续约 **2ms**。所以首帧还存在明显的后端、Shader/管线及初次读回准备成本。需要分别评估显式预热和缓存，不要无差别提高脚本预算或提前解压所有资源。

引擎的 DXC 封装在每次编译调用创建编译对象；当前没有做“去掉 DXC 后是否更快”的同版本受控实验，不能从 39% 的库占比直接推导它占 39% 的首帧时间。

## 6. GPU 已启用，为何仍不跟手

[GpuDevice::finish](../src/graphics/gpu_device.cpp#L53) 明确让 CPU 同步等待 GPU；随后 [read_region](../src/graphics/raster_view.cpp#L340) 把 GPU 图像转为 CPU RGBA；[窗口提交](../src/runtime/view_api.cpp#L707) 再经 SDL 转换/复制到窗口 surface。当前还不是交换链直接呈现。

示例2原生 D3D12 滚轮六帧平均：

| 阶段 | 耗时 |
|---|---:|
| 完整布局 | **1636ms** |
| UIA 更新发布 | 约 38ms |
| 绘制和同步提交 | 约十几 ms |
| 像素读回 | 约 **3.9ms** |
| SDL/GDI 窗口提交 | 约 **0.66ms** |

读回与重复复制是确实存在的成本，但当前并非 1.7 秒卡顿的主要原因。先换 ANGLE/D3D/OpenGL，或者只改窗口提交，无法消除整页重排。SwiftShader 是 CPU 软件 Vulkan 实现，也不应把 active=SwiftShader 写成显卡硬件加速。

## 7. 第三个页面为什么“不动也忙”

原始差异观察页不是纯静态页面：有每秒时钟/数据更新、`requestAnimationFrame`，以及 [320ms 进度定时器](../tests/user-dev-tests/观察和现代Web特性的差异.html#L2293)，更新进度值与文本。

启用原脚本和原生 UIA后，不触发用户滚动的十二次 render：

| 条件 | 静止调用中位数 | 十二次内完整布局 |
|---|---:|---:|
| Raster，脚本保留 | **370.2ms** | 12次 |
| D3D12，脚本保留 | **392.6ms** | 12次 |
| ANGLE GL，脚本保留 | **357.0ms** | 12次 |
| Raster，首次加载后仅在诊断环境取消定时器 | **0.0085ms** | **0次** |

控制组只通过 API 在诊断进程取消 timer，没有改用户 HTML，也不是产品修复。它证明持续工作来自定时任务所触发的失效，而非每次空 render 都必然重绘。

原始十二帧中样式准备总约 **1400ms**、布局约 **3045ms**，但 paint 总计只有约 **0.003ms**：即使可见画面最终没有变化，也为全局文档版本重做了样式与布局。一个进度/文本的小范围修改会提高全局 revision，当前缺少足够细的样式、布局和绘制失效传播。

当一次处理已经接近 370ms，而页面定时器周期是 320ms，处理结束时下一轮更新往往又已到期；用户输入也在同一 UI 线程处理，因此会感到持续繁忙、延迟和不跟手。任务预算当前没有覆盖后续完整渲染成本，不能靠延长脚本超时解决。

WebTest 还在每轮执行完成后固定再 sleep 16ms，见 [主循环](../apps/webtest/main.cpp#L294)。这不是秒级卡顿的主因，但会把已有绘制时间再加到输入响应间隔上，布局优化后应改成由任务截止时间、帧需求和平台消息共同驱动等待。

## 8. 建议的实施顺序

1. **优先拆开纯滚动与重新布局。** 保留内容布局/文字结果/语义身份；滚动只更新变换、裁剪、命中与 AX 几何及必要事件。正确覆盖嵌套 scrollport、负偏移、选择/光标和旧快照，不能仅移动显示像素而留下错误命中。目标首先是纯滚动 `layout_frames` 不再每帧增加。
2. **细化 DOM 修改的失效。** 将几何无关、样式相关和结构相关的代次分开；普通文本/进度修改不应重跑全部 CSS cascade。保持 `:has`、继承变量、生成内容、媒体条件与 AX 正确传播，使用子树/依赖关系确定范围。
3. **文字和计算样式缓存。** 缓存跨帧保留，区分内在测量与最终段落、按实际内存预算管理并避免大规模线性扫描。先用三页记录 hit/miss 和布局阶段计数验收益，不能只扩大预算或用新测试镜像实现。
4. **AX 增量化。** 重用角色/名称/关系，只对滚动更新几何和可见性；变更发布合并，不以禁用 UIA 或隐藏节点语义为性能方案。
5. **GPU 与呈现。** 前述 CPU 问题缓解后再做滚动层合成、减少同步等待、交换链/共享纹理直呈；同时保留 Raster 与设备丢失恢复。冷启动准备按实际使用显式预热，完整 Shader/管线缓存另测。
6. **体积单列治理。** 保留完整引擎总目标，提供可追溯的构建能力配置，评估不同后端闭包及静态调试信息交付。不能默认删除 DXC/SwiftShader 或只拿轻量预览包替代完整 SDK。正式 Release 在相同源码上另行测量，不能拿旧 Release 大小充当当前结果。

建议验收同时记录三页原文哈希、实际 active 后端、首次 render、程序滚动/原生消息滚动的中位数和 p95、布局次数、文字 miss、损伤面积、像素一致性、AX/命中和静止跳过。当前纯滚动全部样本均超过 33ms，更不用说 16.67ms；本轮没有把建议写成“优化完成”。

## 10. 后续复核：Linux 为何没有 DXC，动态库仍接近 Windows

2026-11-04 针对用户的动态库体积疑问，另取**同一源码指纹** `bbb5c31f2466f0e402b1ba577b544226f6909ecb9f2fdc4d1b89430835b1dd59` 的两端相对定位阶段包复核。前文是调查开始时的历史样本，本节不覆盖旧值或混合不同阶段。Linux 没有 DXC，Skia Direct3D 与 ANGLE D3D11 均关闭；Windows/ELF 交付元数据的差异使原始文件总大小看起来接近。

证据：[同源动态库复核及副本剥离对照](../build/reports/dynamic-size-recheck/20261104T054434Z-f6b7757c/report.json)。Windows 取包 `20261104T042855Z-086f8986`，Linux 取 `20261104T043312Z-90bdaebd`，两包原任务均 passed，完整 SDK SHA256 已重核。

| 内容 | Windows 原包 DLL | Linux 原包 SO | Linux 剥离对照副本 |
|---|---:|---:|---:|
| 文件总大小 | **125.10 MiB** | **106.67 MiB** | **66.19 MiB** |
| `.text` 机器代码 | **94.46 MiB** | **42.61 MiB** | **42.61 MiB** |
| 普通符号与字符串表 | 无同类大表，PDB 独立交付 | **40.49 MiB** | **0** |
| `.pdata` 或 `.eh_frame`＋`.eh_frame_hdr` | 6.78 MiB | 11.16 MiB | 11.16 MiB |

这些行不是完整节总和表；ELF 异常展开信息与 PE 的格式不同，不能逐项等价或当作无用调试信息删除。代码节的跨平台差额也包含工具链与平台实现差异，不能全部归为 DXC。

Linux 原 SO 精确 **111,854,856 字节**，SHA256 `cd443ce1e04f7eb957b2b0c07b4afcc26e91aefd3d7d8a9d6ab8848cf4431309`。只在受控 `build/` 暂存副本执行 `llvm-objcopy --strip-unneeded original.so stripped.so`，得到 **69,403,056 字节**，SHA256 `89d9f9707486d0a56f83ee36c794b8ff07abfb4eedd50f997578bc8eab0bec10`，减少 **42,451,800 字节／40.49 MiB**。两个普通表占原文件约 37.95%；剥离没有减少机器代码。Windows DLL 精确131,174,400字节，SHA256 `02d71bac6fe287beab21406f19b3ba4ad577a68e6e7796f82b7a9cf983b27249`。

验证不仅比较文件大小：

- ELF 全部 `SHF_ALLOC` 节的类型、标志、地址、大小和文件内容哈希逐项一致（NOBITS 检查属性和大小），动态定义导出111项逐字一致，NEEDED仍仅 `libc.so`。
- 用包内真实 `WebTest.bin` 和 musl loader，在 WSL 分别加载原包 SO 与剥离副本；三份原始网页各做 Raster 首帧，示例2另做实际 active=6 的 SwiftShader 首帧，共8次调用全部退出0。
- 四组原库/剥离副本的 PPM 像素 SHA256 逐组完全一致；用户原页哈希未变。检查关闭脚本，属于首帧绘制和所选后端的定向验证，不是完整运行契约、性能或发布验收。
- 首个探针误将绝对页面路径传给 WebTest，受 UI root 限制失败；改为逻辑相对页面路径后重跑通过，没有修改产品或放宽资源边界。原失败目录 `20261104T054024Z-9bb5f6d6` 保留，不冒报通过。两次解包/剥离/像素暂存均已自动清理。

因此，更准确的解释是：**Linux 的运行代码已经明显少于 Windows，但交付 SO 仍携带约40MiB非运行时普通符号信息，掩盖了文件总大小上的差距。** 现有安装步骤移除 DWARF 并不等于完成全部非运行时符号分离。后续可改进安装副本的符号剥离与独立符号包关联；本节仅完成隔离对照，没有替换正式 SO、改发布脚本、重建依赖或生成 SDK。
